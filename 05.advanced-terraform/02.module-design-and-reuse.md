# Module design and reuse

Modules are how huge infra stays DRY. Bad modules (one module that creates the VPC, EKS, and the app) are worse than copy-paste.

### 1. Four layers of reuse

```text
1. Resource          aws_lb, aws_instance          — do not wrap one-for-one
2. Building-block    vpc, alb, rds                 — small, stable
3. Pattern           "ecs service + alb + logs"    — how your company deploys
4. Root / live       prod/app                      — env wiring only
```

- **Building-block**: reusable everywhere, few opinions.
- **Pattern**: opinionated. Hides 70 options. Roots call these.
- **Root**: `dev` vs `prod` values, backend key, provider.

>[!NOTE]
>
> Do not write `module "vpc"` that only forwards 80 variables to the official AWS VPC module. Either **use** that official module, or write a **wrapper** that hides most options.

### 2. Inputs (variables of a module)

- **Required** = things that must differ (`name`, `vpc_id`, instance class).
- **Optional with defaults** = your opinions (log retention, tags).
- Avoid a giant `extra_settings` object "just in case". That is not an API, it is a leak.

```tf
variable "name" {
  type        = string
  description = "Name prefix for all resources"
}

variable "vpc_id" {
  type        = string
  description = "VPC where the service runs"
}

variable "instance_type" {
  type        = string
  default     = "t3.micro"
  description = "EC2 type. Override in prod if needed."
}
```

### 3. Outputs

Export **IDs and ARNs** that consumers need. Do not export the whole resource object.

```tf
# GOOD
output "alb_arn" {
  value = aws_lb.this.arn
}

output "alb_dns_name" {
  value = aws_lb.this.dns_name
}

# BAD — leaks internals, breaks when the resource changes
output "alb" {
  value = aws_lb.this
}
```

### 4. Composition (modules calling modules)

```tf
# modules/web-stack/main.tf  (pattern module)
module "alb" {
  source = "../alb"
  name   = var.name
  vpc_id = var.vpc_id
}

module "service" {
  source           = "../ecs-service"
  name             = var.name
  vpc_id           = var.vpc_id
  target_group_arn = module.alb.target_group_arn
}
```

- Building-blocks stay small.
- Pattern modules wire them.
- Roots only pass env values.

### 5. Version modules like a library

When the module lives in its own Git repo (see `13.consume-modules-from-git.md`):

- Tag releases: `v1.0.0`, `v1.1.0`, `v2.0.0`
- New **optional** variable → minor (`v1.1.0`)
- Removed / renamed input or output → major (`v2.0.0`)
- Write a `CHANGELOG` in the module repo

### 6. The god module (anti-pattern)

```tf
# BAD
module "everything" {
  source      = "./modules/god"
  create_vpc  = true
  create_eks  = true
  create_app  = var.env == "prod"
}
```

Problems:

- One `plan` sees network + cluster + app
- Teams block each other
- `count` / flags make the graph unreadable
- You cannot pin "VPC v1.2" independently from "app v3.0"

>[!WARNING]
>
> Start every new piece of infra as a **module**, but keep each module to **one job**. A library of small modules is the goal, not one module with 40 `create_*` flags.
