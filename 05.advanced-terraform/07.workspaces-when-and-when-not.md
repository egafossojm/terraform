# Workspaces: when and when not

"Workspace" means **two different things**. Do not confuse them.

### 1. CLI workspaces (same directory, multiple states)

Terraform starts with a workspace named `default`. Extra workspaces are extra **state files** for the **same configuration**.

```bash
$ terraform workspace show
default

$ terraform workspace list
$ terraform workspace new dev
$ terraform workspace new prod
$ terraform workspace select prod
$ terraform workspace delete dev
```

With a local backend you get:

```text
terraform.tfstate.d/dev/terraform.tfstate
terraform.tfstate.d/prod/terraform.tfstate
```

With S3, the backend stores a different state object per workspace name.

People then write:

```tf
locals {
  instance_type = terraform.workspace == "prod" ? "t3.medium" : "t3.micro"
}
```

### 2. Why this is dangerous for huge infra

- Same working directory for prod and dev → easy to `select prod` by mistake
- Same code path → lots of `count = terraform.workspace == "prod" ? 1 : 0`
- Backend configuration is awkward (one `key` + workspace prefix)
- Reviews cannot see "this PR only touches prod" by path
- `default` cannot be deleted and people forget which workspace they are in

```bash
$ terraform workspace show
# if this prints "prod" and you thought you were in dev...
```

>[!WARNING]
>
> Do **not** use CLI workspaces as the way to separate **prod vs dev** of a large platform. Use **directories** (previous lesson).

### 3. When CLI workspaces are OK

- Many **identical** throwaway stacks (PR preview env `pr-142`)
- A workshop with one folder and 3 student states
- A tiny personal project

Even then, name them clearly and never apply without `workspace show`.

### 4. Terraform Cloud / HCP **workspaces** (different meaning)

In chapter `03` you created a TFC workspace (`DevOps-Prod`). That is a **remote run + remote state** named object. It is closer to "**one root** in the cloud", not to `terraform workspace new`.

Typical mapping:

| Idea | CLI | Terraform Cloud |
|---|---|---|
| One root, one state | one directory | one TFC workspace |
| Extra CLI workspace | `workspace new` | usually **another** TFC workspace, not `terraform.workspace` |

```tf
terraform {
  cloud {
    organization = "terraform-zero-to-mastery"
    workspaces {
      name = "prod-network"
    }
  }
}
```

One TFC workspace per live root (`prod-network`, `prod-app`, `dev-app`) is a good pattern. That is **directory-per-env**, hosted remotely — not `if terraform.workspace == "prod"`.

### 5. Rule

- **Need isolation for real environments** → directories (or one TFC workspace per root).
- **Need many short-lived copies of the same root** → CLI workspaces *can* work.
- **Never** use `terraform.workspace` as your main configuration language.
