# Huge infra mental model

At small scale, Terraform feels like a script: write resources, `apply`, done.

At huge scale, Terraform is a **desired-state compiler**. The syntax is the easy part. The hard parts are **state**, **boundaries**, and **change**.

### 1. What Terraform does on every run

1. Read `.tf` files + variables
2. Read **state** (what Terraform last believed exists)
3. Call providers and build a **dependency graph**
4. **Plan** = the diff (config vs state vs real cloud)
5. **Apply** = mutate the cloud and write state again

```text
configuration (.tf)  +  state  +  real infrastructure
                         |
                    terraform plan
                         |
                    create / update / destroy
```

If you forget this model, you will treat Terraform like Ansible (run steps) instead of like a compiler (declare the end state).

### 2. Problems that appear when infra is huge

| Problem | What actually hurts |
|---|---|
| **State** | Locking, secrets in state, drift, one lock for everything |
| **Boundaries** | Who owns which stack? What depends on what? |
| **Change** | Review, promote to prod, rollback, blast radius of one PR |
| **Reuse** | Copy-paste vs modules vs one giant "do everything" module |
| **Identity** | How CI authenticates to the cloud and to private module repos |

### 3. Root module vs reusable module (at scale)

You already know this from `04.terrform-module`. The rule gets stricter:

- A **root module** is a directory you `init` / `plan` / `apply`. It owns **one state file**.
- A **reusable (child) module** is a package. Nobody applies it directly in production. Roots **call** it.

```tf
# This file lives in a ROOT: live/prod/app/main.tf
module "web" {
  source = "git::https://github.com/org/terraform-aws-web.git?ref=v1.4.2"

  name   = "checkout"
  vpc_id = var.vpc_id
}
```

**Thin roots, thick modules:**

- Roots contain: `backend`, `provider`, module calls, a few `locals`.
- Modules contain: the real `resource` blocks.
- Do **not** put `backend {}` inside a shared module. Backend belongs to the root (the state owner).

### 4. Blast radius

**Blast radius** = how much cloud can one `terraform apply` change or destroy.

- One state for "all of prod" → one lock, 40 minute plans, one bad apply can touch RDS + IAM + DNS.
- Many small states (`prod/network`, `prod/app-checkout`) → a mistake in the app stack cannot destroy the VPC.

>[!NOTE]
>
> The rest of this chapter is mostly: **shrink blast radius**, **reuse modules**, **pin versions**, **promote changes through Git**.

### 5. One sentence to remember

**Many small state files + versioned modules + one environment = one root + Git as the change log + CI as the only applier.**
