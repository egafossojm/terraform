# Provisioners and terraform_data

You used **user data** in `00` (`10.vm-command-at-startup.md`). That is the right direction.

`provisioner` looks powerful and causes pain at scale.

### 1. What provisioners are

```tf
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  provisioner "remote-exec" {
    inline = [
      "sudo yum install -y nginx",
      "sudo systemctl start nginx"
    ]

    connection {
      type        = "ssh"
      user        = "ec2-user"
      private_key = file("~/.ssh/id_rsa")
      host        = self.public_ip
    }
  }
}
```

Terraform SSHs in **during apply** and runs commands.

Problems:

- Not a real desired-state object (hard to show in plan)
- Fail halfway → instance exists, software does not
- Needs network + SSH keys in CI
- Re-create vs re-run is confusing
- Does not scale to 200 instances

HashiCorp's own guidance: **provisioners are a last resort**.

### 2. What to use instead

| Need | Prefer |
|---|---|
| Packages / services on a VM | User data, cloud-init, golden AMI |
| Config after boot | SSM, Ansible **outside** Terraform, or an operator |
| K8s manifests | Helm / Argo CD, not `local-exec kubectl` |
| One-shot DNS / API call | A real provider resource if it exists |

```tf
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"
  user_data     = file("${path.module}/user_data.sh")
}
```

### 3. `local-exec` as glue (still last resort)

```tf
resource "null_resource" "invalidate" {
  triggers = {
    ui_hash = var.ui_hash
  }

  provisioner "local-exec" {
    command = "aws cloudfront create-invalidation --distribution-id ${var.cf_id} --paths '/*'"
  }
}
```

This runs on the **machine that applies** (your laptop or CI). It will not run for teammates who only `plan`. Prefer a CloudFront resource or a CI step **after** apply.

### 4. `terraform_data` (modern replacement for many `null_resource`s)

`terraform_data` is a resource that stores an `input` and can be replaced when something else changes.

```tf
resource "terraform_data" "bootstrap" {
  input = var.cluster_name

  triggers_replace = [
    aws_eks_cluster.this.id
  ]
}
```

Use it as a **graph node** (something else `depends_on` it) or with `lifecycle.replace_triggered_by`. Still avoid stuffing shell scripts into it unless you have no provider.

### 5. `file()`, `templatefile()`, `cloudinit_config`

Keep startup config **in Git**, rendered by Terraform, executed by the instance:

```tf
user_data = templatefile("${path.module}/user_data.sh.tftpl", {
  env     = var.environment
  db_host = var.db_host
})
```

Do not put secrets in user data if you can use IAM + Secrets Manager on the instance instead (user data is visible on the instance metadata).

>[!NOTE]
>
> If you need config management, use a **config management tool**. Terraform's job is to create the machine and the IAM that lets that tool run.
