# State refactoring: moved, import, rm

Huge infra is refactored often: a resource moves into a module, a name changes, an old bucket must be adopted.

**Goal:** change the **address in state** without destroying the real cloud object.

### 1. Addresses

Terraform tracks objects by **address**, not by the AWS name tag.

```text
aws_instance.my_vm
aws_instance.my_vm[0]              # count
aws_instance.my_vm["web"]          # for_each
module.web.aws_lb.this
```

```bash
$ terraform state list
$ terraform state show aws_instance.my_vm
$ terraform show
```

If you rename `aws_instance.my_vm` to `aws_instance.web` in code **without** telling state, Terraform plans:

- destroy `aws_instance.my_vm`
- create `aws_instance.web`

That is a new VM, not a rename.

### 2. `moved` block (prefer this)

Put the move **in code**. The same PR that renames the resource also records the history.

```tf
# old: resource "aws_instance" "my_vm" { ... }
# new: resource moved into module.web

moved {
  from = aws_instance.my_vm
  to   = module.web.aws_instance.this
}
```

```bash
$ terraform plan
# should say: move, not destroy + create
```

After apply, you can delete the `moved` block in a later PR (or keep it for a while).

`removed` tells Terraform to drop an address from state **without** destroying the object (Terraform 1.7+):

```tf
removed {
  from = aws_instance.legacy

  lifecycle {
    destroy = false
  }
}
```

### 3. CLI surgery (know it, use less)

| Command | Use |
|---|---|
| `terraform state list` | See addresses |
| `terraform state mv OLD NEW` | Rename address (like `moved`) |
| `terraform state rm ADDR` | Stop managing; leave object in the cloud |
| `terraform state pull` | Download state (break-glass) |
| `terraform state push` | Upload state (dangerous) |

```bash
$ terraform state mv aws_instance.my_vm module.web.aws_instance.this
$ terraform state rm aws_instance.legacy
```

>[!WARNING]
>
> - Do not edit `terraform.tfstate` by hand.
> - `state push` can destroy the team history. Prefer `moved` / `import` in code.
> - `state rm` does **not** delete the AWS object. The next apply will ignore it unless you import it again.

### 4. Import existing infrastructure

When the object already exists in AWS (created by click-ops or another tool).

**Modern: `import` block**

```tf
resource "aws_s3_bucket" "logs" {
  bucket = "org-prod-logs-123"
}

import {
  to = aws_s3_bucket.logs
  id = "org-prod-logs-123"
}
```

```bash
$ terraform plan    # should show import, then maybe small updates
$ terraform apply
```

After a successful import, remove the `import` block.

**Classic CLI:**

```bash
$ terraform import aws_s3_bucket.logs org-prod-logs-123
```

You still need the `resource` block in code. Import only binds the id into state.

### 5. Safe refactor checklist

1. `terraform state list` — know the current address
2. Change the `.tf` address
3. Add `moved` (or `state mv`) **in the same change**
4. `terraform plan` — **zero** destroys for that object
5. Apply
6. Import leftover click-ops objects in **small slices**, not the whole account in one day

>[!NOTE]
>
> `prevent_destroy` in `lifecycle` does **not** protect you from `state rm`. It only fails an apply that would destroy the resource through the graph.
