# Split state and blast radius

You learned in `00` and `03` that Terraform is **stateful** and that production state must be **remote + locked**.

At huge scale, the next rule is: **one apply = one state = one blast radius**.

### 1. Why one giant state fails

A single state for "all of prod" means:

- One lock: nobody else can apply until you finish
- One `plan` that takes a very long time
- One bad apply can destroy a database **and** change IAM **and** DNS
- Every team waits on the same pipeline

### 2. How to split

Split by **blast radius** and **team ownership**, not only by AWS service name.

Good splits:

- `network` — VPC, subnets, TGW (changes rarely, high blast radius)
- `platform` — EKS, shared RDS, Kafka
- `security` — org IAM, GuardDuty (tight ACL on this state)
- `app-checkout`, `app-billing` — frequent deploys, smaller blast radius

Each split = its own **root directory** + its own **backend key**.

```text
live/
  prod/
    network/     → s3 key prod/network/terraform.tfstate
    platform/    → s3 key prod/platform/terraform.tfstate
    apps/
      checkout/  → s3 key prod/apps/checkout/terraform.tfstate
```

### 3. Remote backend per root

You already configured S3 + `use_lockfile` in chapter `03`. At scale, only the **key** changes per root:

```tf
terraform {
  backend "s3" {
    bucket       = "org-tf-state-prod"
    key          = "prod/network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

Requirements for every production state:

- Remote
- Encrypted
- Locked
- Access-controlled (IAM)
- Versioned (S3 versioning or Terraform Cloud state versions)

>[!WARNING]
>
> Local `terraform.tfstate` is for a laptop lab only. Never share it on Slack or commit it.

### 4. What "one state" should contain

Ask: **If this apply goes wrong, what is the worst it can destroy?**

- If the answer is "the company network + all apps" → split.
- If the answer is "this one service" → good size.
- If you have 3 resources and 30 states → too small (apply order becomes hell).

### 5. Bootstrap state (chicken and egg)

The S3 bucket and lock that store state must live **somewhere**.

Common pattern:

- A tiny `_bootstrap` root (or a one-time click) creates the state bucket.
- Extra approval to change `_bootstrap`.
- Everything else uses that bucket.

```text
live/_bootstrap/     # state bucket, org trail — applied rarely
live/prod/network/   # uses that bucket
```
