# Anti-patterns and a target skeleton

Memorize the anti-patterns. Copy the skeleton when you start a real live repo.

### 1. Anti-patterns

1. **One state for the company** — one lock, one disaster.
2. **CLI workspaces for prod vs dev** of a big platform — easy to apply the wrong env.
3. **`count` over lists that get reordered** — mass replace.
4. **`source = "...?ref=main"`** — yesterday's apply is not today's plan.
5. **Git submodule as the Terraform module manager** — two pins, empty folders.
6. **Provisioners as config management** — SSH from apply, half-failed VMs.
7. **`terraform apply` on a laptop to prod** — no audit, wrong credentials.
8. **Secrets in Git** or printed to Slack / public PR comments.
9. **God module** (`create_vpc && create_eks && create_app`).
10. **`-target` as the standard deploy** — hidden drift.
11. **Long-lived `dev` / `prod` Git branches** for the same live tree.
12. **Ignoring `.terraform.lock.hcl`** — provider roulette.
13. **`terraform_remote_state` as a general-purpose database** — tight coupling + secret leakage.
14. **Thin wrapper modules** with 80 passthrough variables and no opinions.
15. **Mixing `backend {}` and `cloud {}`** — they cannot coexist.

### 2. Target skeleton (huge org)

```text
# github.com/org/terraform-modules   (or one repo per module)
# tagged vX.Y.Z

# github.com/org/terraform-live
live/
  _bootstrap/              # state bucket — rare apply, extra approval
  dev/
    network/
    platform/
    apps/checkout/
  staging/
    network/
    platform/
    apps/checkout/
  prod/
    network/
    platform/
    apps/checkout/
```

Each `live/*/**` root contains:

```text
backend.tf                 # key = "prod/apps/checkout/terraform.tfstate"
versions.tf                # terraform + providers
providers.tf               # default_tags, assume_role
main.tf                    # module calls only
variables.tf
outputs.tf
terraform.tfvars           # non-secret env values
.terraform.lock.hcl
```

Pipeline: path filter → plan/apply only the root that changed (and its dependents if needed).

### 3. Checklist before you call it "production"

- [ ] Remote state, encrypted, locked, versioned, IAM-restricted
- [ ] State split by blast radius / team
- [ ] Modules versioned (`ref=vX.Y.Z` or registry `version`)
- [ ] `.terraform.lock.hcl` committed in roots
- [ ] Directory-per-env (or one TFC workspace per root)
- [ ] Plan on PR, apply on merge, OIDC to the cloud
- [ ] `CODEOWNERS` + extra approval on `live/prod`
- [ ] Secrets not in Git; `sensitive` on outputs; state ACL tight
- [ ] `for_each` + maps for anything that grows
- [ ] `moved` for renames, not destroy/create
- [ ] fmt / validate / lint / policy on every PR
- [ ] `prevent_destroy` on irreplaceable data stores
- [ ] Document apply order and break-glass unlock

### 4. Learning order (if you redo this chapter)

1. State split + remote backend + lock
2. Module I/O + `for_each` + `moved`
3. Directory-per-env live repo + pin module `ref`
4. CI plan-on-PR, apply-on-merge, OIDC
5. `terraform test` + tflint + Checkov
6. Multi-account providers
7. Terragrunt / Atmos **only if** root boilerplate hurts
8. TFC / Spacelift when people and drift exceed GitHub Actions

### 5. Two decisions that unlock the rest

1. **Directory-per-env** vs Terragrunt (start with directories)
2. **Modules in this repo** vs **separate GitHub repos + tags**

Everything in this chapter hangs off those two choices.

>[!NOTE]
>
> You do not need every tool on day one. You need **small states**, **pinned modules**, and **no apply to prod without a plan someone read**.
