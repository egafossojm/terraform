# Stack communication

After you split state, stacks must pass values (VPC id, subnet ids, DNS zone). Do this with a **contract**, not by peeking inside another team's state file for 20 attributes.

### 1. Preferred: pass IDs as variables

The app root does not know where the VPC state lives. CI (or you) injects the id.

```tf
# live/prod/apps/checkout/variables.tf
variable "vpc_id" {
  type        = string
  description = "VPC id from the network stack"
}

# live/prod/apps/checkout/main.tf
module "web" {
  source = "git::https://github.com/org/terraform-aws-web.git?ref=v1.4.2"
  vpc_id = var.vpc_id
}
```

```bash
# After the network stack was applied
$ terraform output -raw vpc_id
vpc-0aa11aa98e9111f53

$ terraform apply -var="vpc_id=vpc-0aa11aa98e9111f53"
```

In CI, a wrapper (or Terragrunt) can read the producer output and pass it in.

### 2. Common: `terraform_remote_state`

The consumer reads the producer **state** and uses its outputs.

```tf
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "org-tf-state-prod"
    key    = "prod/network/terraform.tfstate"
    region = "eu-west-1"
  }
}

module "web" {
  source = "git::https://github.com/org/terraform-aws-web.git?ref=v1.4.2"
  vpc_id = data.terraform_remote_state.network.outputs.vpc_id
}
```

The network stack **must** export a stable output:

```tf
# live/prod/network/outputs.tf
output "vpc_id" {
  value = module.vpc.vpc_id
}
```

>[!WARNING]
>
> `terraform_remote_state` couples stacks:
> - The consumer must be allowed to **read** the producer state (secrets may be there).
> - If the producer **renames** an output, the consumer breaks.
> - Apply **order** is now mandatory: network first, then app.

Use it for a **few** well-named outputs (`vpc_id`, `private_subnet_ids`). Do not treat another team's state as a database.

### 3. Better at scale: a contract outside Terraform state

Write IDs to a well-known place. Consumers use a **data source**.

Examples:

- AWS SSM Parameter Store
- AWS Secrets Manager (for secrets)
- A small "registry" stack that only publishes outputs

**Producer (network root):**

```tf
resource "aws_ssm_parameter" "vpc_id" {
  name  = "/prod/network/vpc_id"
  type  = "String"
  value = module.vpc.vpc_id
}
```

**Consumer (app root):**

```tf
data "aws_ssm_parameter" "vpc_id" {
  name = "/prod/network/vpc_id"
}

module "web" {
  source = "git::https://github.com/org/terraform-aws-web.git?ref=v1.4.2"
  vpc_id = data.aws_ssm_parameter.vpc_id.value
}
```

Benefits:

- App stack does not need IAM on the network **state** file
- You can rebuild the network root without every consumer knowing the state key
- The parameter name **is** the API

You can also look up by tags:

```tf
data "aws_vpc" "prod" {
  tags = {
    Environment = "prod"
    Role        = "main"
  }
}
```

### 4. Apply order

```text
_bootstrap  →  network  →  platform  →  apps
```

- Document the order in the live repo README.
- In CI, path filters apply only the stack that changed, but a **network** change should trigger app plans too (or at least a warning).
- Orchestrators (lesson `20`) can encode this graph.

### 5. What not to do

- Do not `terraform_remote_state` into 20 attributes of another team.
- Do not share one state "so we do not need to pass outputs".
- Do not hardcode `vpc-0aa11...` in `main.tf` (use tfvars, SSM, or remote state).
