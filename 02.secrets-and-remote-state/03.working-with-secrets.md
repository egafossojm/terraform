# Secrets

Three layers, from weakest to strongest:

| Mark | Effect |
|---|---|
| `sensitive = true` | Redacts CLI output. Value is still in state and in the plan. |
| `ephemeral = true` (Terraform 1.10+) | Value exists only for this operation. Not written to state or plan. |
| Write-only argument (Terraform 1.11+) | Provider receives the value and Terraform discards it. Pair it with a `*_wo_version` so you can rotate. |

Encrypt remote state either way. `sensitive` is not encryption.

## Pattern: read at apply time, accept state storage

A normal `data` source result is stored in state. Acceptable for non-secret lookups. Poor for passwords.

```hcl
data "aws_secretsmanager_secret_version" "db" {
  secret_id = "db_secrets"
}

locals {
  db = jsondecode(data.aws_secretsmanager_secret_version.db.secret_string)
}
```

## Pattern: ephemeral read + write-only argument

The secret never lands in the plan or the state. Requires Terraform 1.11+ and a resource argument that is write-only (`password_wo` on `aws_db_instance`, `value_wo` on `aws_ssm_parameter`, and similar).

```hcl
ephemeral "aws_secretsmanager_secret_version" "db" {
  secret_id = "db_secrets" # JSON: {"username":"app","password":"..."}
}

locals {
  db_password = jsondecode(ephemeral.aws_secretsmanager_secret_version.db.secret_string)["password"]
}

resource "aws_db_instance" "app" {
  identifier          = "app"
  engine              = "mysql"
  instance_class      = "db.t3.micro"
  allocated_storage   = 20
  username            = "app"
  password_wo         = local.db_password
  password_wo_version = 1
  skip_final_snapshot = true
}
```

`secret_string` is the decrypted value. A local computed from an ephemeral value stays ephemeral: feed it to a write-only argument or an output marked `ephemeral = true`. A normal output or a normal argument stores it again.

Terraform cannot diff a write-only value, because it is not in state. Bump `password_wo_version` when the secret should be sent again.

Generate a password in-config with `ephemeral "random_password"` the same way, and write it to Secrets Manager through a write-only argument so the next boot can read it.

## Vault

Use the Vault provider to read KV (or use an ephemeral Vault resource when the provider offers one) and pass the value to a write-only argument.

```hcl
data "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "db"
}
```

A plain `data` read still stores the secret in state. Prefer the provider's ephemeral resource plus `password_wo` when both exist.

## Rules that survive the interview

- Secrets live in a secret store. Git holds the name of the secret, not the value.
- CI uses OIDC. No long-lived `AWS_ACCESS_KEY_ID` in the repo or in a tfvars file.
- Root outputs that contain secrets are `sensitive`. Plan comments in pull requests stay in a private repo.
- User data and Terraform state are both readable by more people than you think. Design so the password is not in either.
