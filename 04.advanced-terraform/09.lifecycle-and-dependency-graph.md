# Lifecycle and the dependency graph

Terraform builds a graph from interpolations (`subnet_id = aws_subnet.web.id`). You can add **seatbelts** (`lifecycle`) and rare **manual edges** (`depends_on`).

### 1. `lifecycle` meta-argument

```tf
resource "aws_lb" "this" {
  name = var.name
  # ...

  lifecycle {
    create_before_destroy = true
    prevent_destroy       = true
    ignore_changes        = [tags["LastTouchedByOps"]]
    replace_triggered_by  = [aws_security_group.this.id]
  }
}
```

| Argument | Meaning |
|---|---|
| `create_before_destroy` | Create the replacement **first**, then destroy the old (ALB, launch templates, some IAM names) |
| `prevent_destroy` | Fail the apply if this resource would be destroyed (prod DB, KMS) |
| `ignore_changes` | Do not revert listed attributes if something else mutates them |
| `replace_triggered_by` | Force replace this resource when another address changes |

>[!WARNING]
>
> - `prevent_destroy` is a seatbelt, not a backup. `terraform state rm` bypasses it.
> - `ignore_changes = all` means Terraform no longer manages that object. Use it only as a temporary bridge.

### 2. `depends_on`

Terraform usually infers order. Use `depends_on` when there is a **hidden** dependency (API is ready only after another resource exists, but no attribute is referenced).

```tf
resource "aws_route" "default" {
  route_table_id         = aws_route_table.public.id
  destination_cidr_block = "0.0.0.0/0"
  gateway_id             = aws_internet_gateway.this.id

  depends_on = [aws_internet_gateway.this]
}
```

>[!NOTE]
>
> Use **sparingly**. `depends_on` on a **whole module** serializes the apply and makes plans larger. Prefer passing an attribute (`vpc_id = module.network.vpc_id`).

### 3. Preconditions and postconditions

Encode invariants so a bad variable fails **before** it creates a broken network.

```tf
variable "azs" {
  type = list(string)
}

resource "aws_subnet" "this" {
  # ...

  lifecycle {
    precondition {
      condition     = length(var.azs) >= 2
      error_message = "Need at least 2 availability zones."
    }
  }
}
```

`postcondition` runs after the resource is read (example: bucket is not public).

### 4. `check` blocks (assertions on the stack)

```tf
check "at_least_two_public_subnets" {
  assert {
    condition     = length(local.public_subnet_ids) >= 2
    error_message = "Need 2+ public subnets for a load balancer."
  }
}
```

Failed checks warn (or fail, depending on version/settings). They do not always block apply — read them on the plan.

### 5. `-target` is a hotfix, not a workflow

```bash
$ terraform apply -target=aws_security_group.this
```

This updates **only** that address and its dependencies. It can leave the rest of the stack **inconsistent**.

>[!WARNING]
>
> Do not make `-target` your standard deploy. Use it to unblock a broken apply, then run a **full** plan.

### 6. Graph commands

```bash
$ terraform graph | dot -Tpng > graph.png
$ terraform plan -generate-config-out=generated.tf   # helper for import
```

You rarely need the picture. If the plan order surprises you, you probably need an attribute reference, not more `depends_on`.
