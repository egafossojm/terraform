# Git submodules vs Terraform Git source

You may see this workflow:

```bash
$ git submodule add <remote_url> [<destination_folder>]
$ git commit -m "added submodule"
$ git push
```

That is a **Git** feature. It is not how Terraform wants to consume modules.

### 1. What those commands do

1. Clone `remote_url` into `destination_folder`
2. Record in the **parent** repo:
   - `.gitmodules` — URL and path
   - a **gitlink** — exact commit SHA of the child repo
3. Commit and push that **pointer**

The parent does **not** copy the child's file history. It stores: "at this path, use commit `abc123` of that other repo."

Everyone else must clone with submodules or they get an **empty folder**:

```bash
$ git clone --recurse-submodules <parent_url>
# or later:
$ git submodule update --init --recursive
```

### 2. When a submodule is the right tool

Use it when **all** of these are true:

- The child is its **own** repo (own history, tags, PRs)
- The parent needs those files **in the working tree** at a fixed path (`vendor/foo`, `proto/`, `third_party/sdk`)
- The parent must **pin a commit** and only move that pin on purpose
- Consumers are **Git users** (humans, CI `git clone`), not a tool that already fetches Git itself

Good examples:

- Shared proto / OpenAPI repo used by several services
- Vendored C library the build system expects on disk
- Company `deploy-scripts` checked out next to an app

### 3. How submodule updates work

The child repo can move every day. The parent **stays** on the old SHA until someone updates it:

```bash
$ cd destination_folder
$ git fetch
$ git checkout v1.3.0
$ cd ..
$ git add destination_folder
$ git commit -m "Bump foo submodule to v1.3.0"
$ git push
```

`--remote` follows the branch in `.gitmodules` (often `main`). Convenient, easy to make accidental. For anything serious, checkout a **tag**.

### 4. Why this is a poor fit for Terraform modules

Terraform's `source = "git::...?ref=v1.2.0"` already:

- Clones the module repo
- Pins tag / SHA
- Puts files under `.terraform/modules` (you do **not** commit that)

A submodule would add:

- A second pin (submodule SHA **and** maybe a `ref`)
- Extra clone flags in CI (`--recurse-submodules`)
- Empty directories when someone forgets `submodule update`
- `source = "./modules/vpc"` instead of a versioned Git URL

### 5. Comparison

| | `git submodule add` | Terraform `source = "git::...?ref="` |
|---|---|---|
| Who clones? | Git, into your repo tree | Terraform, into `.terraform/` |
| What you commit | `.gitmodules` + SHA pointer | The `ref=` in `.tf` files |
| Working tree | Files visible at `destination_folder` | Not in your source tree |
| Best for | Source you compile or vendor | Reusable Terraform modules |
| Updates | Bump SHA, commit parent | Bump `ref`, `terraform init -upgrade` |

### 6. Short rule

- **Need the other repo's files inside this Git repo**, pinned, for Git/CI/build → `git submodule add` is appropriate.
- **Need Terraform to load a module from another GitHub repo** → do **not** add a submodule. Use `source` + `ref` (lesson `13`).

Same idea in other ecosystems: Go uses `go.mod`, npm uses a lockfile — not a submodule of the library.
