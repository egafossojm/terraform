# Multi-environment strategies

You need `dev`, `staging`, and `prod`. The question is **how you isolate them**.

There are four patterns. **Do not mix them casually.**

### 1. Separate directories (best default)

```text
live/
  dev/
    network/
    app/
  staging/
    network/
    app/
  prod/
    network/
    app/
```

Each folder is a **root**:

- Own backend `key`
- Own `terraform.tfvars`
- Own `terraform apply`

```tf
# live/prod/app/terraform.tfvars
instance_type = "t3.medium"
vpc_cidr      = "10.2.0.0/16"

# live/dev/app/terraform.tfvars
instance_type = "t3.micro"
vpc_cidr      = "10.10.0.0/16"
```

Both call the **same module version** (or prod stays one version behind):

```tf
module "web" {
  source        = "git::https://github.com/org/terraform-aws-web.git?ref=v1.4.2"
  instance_type = var.instance_type
}
```

**Why this wins for huge infra:**

- Isolation is perfect (wrong apply cannot hit prod state)
- Promotion is a PR: bump `ref` or copy a value into `prod/.../terraform.tfvars`
- Thin roots may look similar. That is OK. Do **not** DRY the roots by merging states.

### 2. Workspaces (`terraform workspace`)

Same code directory, different state names (`dev` / `prod`).

See the next lesson for a deep dive.

**Short rule:** fine for tiny identical sandboxes. **Do not** use for prod vs dev of a large platform.

### 3. `for_each` over environments (one state)

```tf
module "env" {
  for_each = var.environments
  source   = "./modules/stack"
  name     = each.key
  cidr     = each.value.cidr
}
```

One state still contains **all** environments. A bug in the module can plan against prod and dev together.

>[!WARNING]
>
> Acceptable only for a lab or a set of throwaway preview envs. Not for real prod.

### 4. Orchestrators (Terragrunt, Terramate, Atmos)

They generate backends, inject variables, and run many roots in dependency order.

Use when you have **dozens or hundreds** of roots and the thin-root boilerplate (backend block, provider versions) becomes the pain.

They **do not replace modules**. They replace root copy-paste. See lesson `20`.

### 5. How to promote a change

```text
1. Change the module repo → tag v1.5.0
2. PR: live/dev     ref = v1.5.0   → apply, soak
3. PR: live/staging ref = v1.5.0
4. PR: live/prod    ref = v1.5.0
```

- Prod can stay on `v1.4.2` while dev explores `v1.5.0`.
- **Do not** promote by merging a long-lived `dev` Git branch into a `prod` Git branch if those trees already have different backends.

### 6. What differs between envs

Put in **tfvars** (or CI vars):

- CIDRs, instance sizes, replica counts
- Account id / assume role
- Domain names

Keep **the same module source** (or a pinned older `ref` in prod).

Do **not** put this in the module:

```tf
# BAD
instance_type = terraform.workspace == "prod" ? "t3.medium" : "t3.micro"
```

That hides the difference. Put it in `prod/app/terraform.tfvars` instead.

### 7. Accounts vs folders

Best isolation = **separate AWS accounts** (`dev` / `staging` / `prod`) **and** separate live directories.

A stolen `dev` role must not be allowed to apply `prod` state or assume the prod role.
