# Version control best practices

Git is the **change log** of infrastructure. The repo layout decides how safe a PR is.

### 1. Three repo topologies (pick one and stick)

**A. Live + modules monorepo**

```text
modules/vpc/
modules/eks/
live/dev/network/
live/prod/network/
```

- One PR can change a module and one env
- Easy for small/medium teams
- Danger: people apply from `modules/` or one pipeline plans the world

**B. Module repos + one live repo** (common at scale)

- `terraform-aws-vpc` tagged `v1.2.0`
- `terraform-live` consumes `git::...?ref=v1.2.0`
- Live PRs look like: `prod/app: bump web v1.4.2 → v1.5.0`
- Best when **many teams** consume the same modules

**C. One live repo per domain**

- `live-network`, `live-payments`
- Git permissions match AWS / state permissions

>[!NOTE]
>
> Git **submodules** are a fourth option. Use them only if you need another repo's **files in the working tree** for a non-Terraform tool. Terraform Git `source` already versions modules.

### 2. What to commit / never commit

| Commit | Never commit |
|---|---|
| `*.tf`, non-secret `*.tfvars` | `.terraform/` |
| `.terraform.lock.hcl` (roots) | `*.tfstate`, `*.tfstate.*` |
| `moved` / `import` blocks, README, examples | Secrets, `.env`, key files |
| `versions.tf`, backend config or `backend.hcl` | Provider plugins |

Your repo `.gitignore` should already cover state and `.terraform/`.

### 3. Branches vs environments

**GitOps style (recommended):**

- `main` = what is allowed to apply (or apply **on merge** to `main`)
- Feature branch → PR → `terraform plan` as a comment → review → merge → apply
- **Environments are directories** (`live/dev`, `live/prod`), not long-lived Git branches

>[!WARNING]
>
> A long-lived `prod` branch that diverges from `dev` is a classic disaster. You cannot merge "the module bump" without also merging leftover experiments.

Promotion = **same Git history**, different `ref` / tfvars **per directory**.

### 4. CODEOWNERS and protected `main`

```text
# .github/CODEOWNERS
/live/prod/**           @platform-sre
/modules/network/**     @network-team
```

- Protect `main`: reviews required, CI plan must pass
- Extra approval for `live/prod/**`
- Separate AWS accounts so a stolen `dev` role cannot apply prod

### 5. PR shape and commit messages

- Prefer **one stack** (or one module version bump) per PR
- Title: `prod/app: bump web module v1.4.2 → v1.5.0`
- Body: plan summary, **destroy count**, who should approve
- Do not `terraform apply` to prod from a laptop if CI can do it (no audit trail)

### 6. Tagging module repos

```text
v1.0.0   first stable
v1.1.0   new optional variable
v1.1.1   bugfix
v2.0.0   removed variable / renamed output / forced replace
```

Changelog lives **in the module repo**. Live repos only see tags.

```bash
$ git tag -a v1.2.0 -m "Add optional flow logs"
$ git push origin v1.2.0
```

### 7. Backend config in Git

Two styles:

```tf
# committed, env-specific root
backend "s3" {
  bucket = "org-tf-state-prod"
  key    = "prod/app/terraform.tfstate"
  region = "eu-west-1"
  use_lockfile = true
}
```

Or a shared `backend.tf` without values + `backend.hcl` per env:

```bash
$ terraform init -backend-config=backend.hcl
```

Either is fine. **Do not** put secrets in the backend block (use OIDC / instance role). You cannot use normal `variable` interpolation inside `backend {}`.
