# Consume modules from GitHub repos

In `04` you used **local** modules (`source = "../modules/vpc"`).

When each module has **its own GitHub repo**, the live repo consumes them as a **Git source** with a **pinned `ref`**. The module repos can move every day. The live repo adopts a new version only when you change the pin.

### 1. Git source

```tf
module "vpc" {
  source = "git::https://github.com/your-org/terraform-aws-vpc.git?ref=v1.2.0"

  cidr_block = "10.0.0.0/16"
}
```

Shorthand:

```tf
module "vpc" {
  source = "github.com/your-org/terraform-aws-vpc?ref=v1.2.0"
}
```

Private repos (SSH):

```tf
module "vpc" {
  source = "git::ssh://git@github.com/your-org/terraform-aws-vpc.git?ref=v1.2.0"
}
```

Module in a **subdirectory** of that repo (`//` = path inside the repo):

```tf
module "vpc" {
  source = "git::https://github.com/your-org/terraform-modules.git//modules/vpc?ref=v1.2.0"
}
```

### 2. What `ref` can be

| `ref` | When to use |
|---|---|
| **Tag** `v1.2.0` | Default. Repeatable, readable |
| **Commit SHA** | Strongest pin (tags can be moved) |
| **Branch** `main` | Local/dev only. Every `init -upgrade` can change infra |

### 3. How updates work

Terraform does **not** follow module-repo updates automatically.

1. Update the module repo → tag `v1.3.0`
2. In the live repo, change `ref=v1.2.0` to `ref=v1.3.0`
3. Run:

```bash
$ terraform init -upgrade
$ terraform plan
$ terraform apply
```

`terraform init` clones the module into `.terraform/modules`. Without `-upgrade`, Terraform may keep the already downloaded copy.

That is the intended model: the live repo **chooses** when to adopt a new module, like a lockfile for a library.

### 4. Auth for private repos

The machine that runs `terraform init` must clone every module repo.

- **SSH**: deploy key or machine user; CI uses `ssh-agent`
- **HTTPS + PAT**: `git` credentials / `GIT_ASKPASS` / GitHub Actions token
- **GitHub App** for org-wide read access

### 5. Optional: private registry

If you have many modules and want SemVer like other packages:

```tf
module "vpc" {
  source  = "app.terraform.io/your-org/vpc/aws"
  version = "~> 1.2"
}
```

Git sources are enough for most teams. A registry (HCP Terraform, or similar) is useful when you want a catalog and `version` constraints instead of editing URLs.

### 6. Local path vs Git in a monorepo

If modules live **in the same repo** as live:

```tf
source = "../../modules/vpc"
```

This is fine **if** CI always plans every live stack that uses that module. There is no `ref`. A change in `modules/vpc` can affect all envs in one merge — that is the tradeoff.

For many teams and many consumers, **separate module repos + tags** scale better.

### 7. Do not use Git submodules for this

`git submodule add` tracks another repo inside your working tree. Terraform already clones the module.

A submodule would mean: Git clones into `./modules/vpc` **and** Terraform uses `source = "./modules/vpc"`. You then maintain **two** pins. See lesson `15`.

>[!NOTE]
>
> Good practice in each module repo: `README`, `variables.tf`, `outputs.tf`, `examples/`, and tags `vX.Y.Z`.
