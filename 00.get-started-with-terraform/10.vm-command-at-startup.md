# Instance startup config

Boot-time setup belongs to the instance (user data or cloud-init), not to an SSH session from Terraform.

## user_data

```hcl
resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.micro"
  user_data     = file("${path.module}/user-data.sh")
}
```

Render variables with `templatefile` (the `template_file` data source is retired):

```hcl
user_data = templatefile("${path.module}/user-data.sh.tftpl", {
  env = var.environment
})
```

User data is visible in the cloud console and, on EC2, via instance metadata. Keep secrets out of it. Give the instance an IAM role and let it read Secrets Manager or SSM at boot.

Changing user data does not re-run it on an existing instance. A replacement (`user_data_replace_on_change = true`, or `-replace`) does.

## cloud-init

[cloud-init](https://cloud-init.io/) is the cross-cloud first-boot standard. Feed it `#cloud-config` YAML through `user_data`, or build a MIME archive with the `cloudinit_config` data source (`hashicorp/cloudinit`) when you need several parts.

```hcl
data "cloudinit_config" "web" {
  gzip          = true
  base64_encode = true

  part {
    content_type = "text/cloud-config"
    content      = file("${path.module}/cloud-config.yaml")
  }
}
```

`user_data_base64 = data.cloudinit_config.web.rendered` on the instance.

## Provisioners

`remote-exec`, `file`, and `local-exec` SSH or shell out during apply. They sit outside the desired-state model: a failed command can leave the instance up and the software missing. HashiCorp marks them a last resort.

Prefer user data, a golden AMI, or a config tool that runs after Terraform (SSM, Ansible, cloud-init). Longer version: [`04/18`](../04.advanced-terraform/18.provisioners-and-terraform-data.md).
