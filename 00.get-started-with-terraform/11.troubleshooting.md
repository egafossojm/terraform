# Troubleshooting

Work down this list. Most failures are a bad argument, the wrong identity, or a stale plugin cache.

| Step | Command | Tells you |
|---|---|---|
| 1 | `terraform fmt -recursive` | Style, so the error line is readable |
| 2 | `terraform validate` | Unknown blocks, missing required arguments |
| 3 | `terraform console` | Whether an expression evaluates |
| 4 | `aws sts get-caller-identity` | Which AWS principal the provider will use |
| 5 | `terraform plan` | The real diff, including drift |

## Logs

```bash
export TF_LOG=INFO          # TRACE, DEBUG, INFO, WARN, ERROR, OFF
export TF_LOG_PATH=$PWD/terraform.log
export TF_LOG_CORE=INFO     # Terraform Core only
export TF_LOG_PROVIDER=DEBUG
```

`TRACE` is huge. Use `DEBUG` on the provider when the API error is vague. Log files contain secrets; delete them after.

## Failures you will recognize

| Symptom | Look at |
|---|---|
| `Error: Backend initialization required` | Run `terraform init` after a backend or module change |
| `Error acquiring the state lock` | Someone else's apply, or a crashed one. `force-unlock` only if you are sure |
| Plan wants to replace everything | An argument that forces a new resource (AMI, `name` on some resources), or a changed address (`count` index) |
| `Provider produced inconsistent result` | Provider bug or wrong version. Check the lock file |
| Works locally, fails in CI | CLI version, `AWS_PROFILE`, missing `TF_VAR_`, or a module `ref` the CI runner cannot clone |
| Unexpected variable value | Precedence: CLI and `-var-file` beat `*.auto.tfvars`, which beat `terraform.tfvars`, which beat `TF_VAR_*` |

`terraform plan -refresh-only` shows drift (console edits) without changing infrastructure. A later apply will revert that drift to match config, unless the attribute is in `ignore_changes`.
